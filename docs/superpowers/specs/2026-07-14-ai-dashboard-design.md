# AI Dashboard — Design Specification

## Overview

A comprehensive dashboard system for orchestrating and monitoring AI model conversations, designed to work alongside the existing Deepseek proxy. The system provides real-time monitoring, diagnostics, chat correlation, and account management through a web-based single-page application.

## Architecture

### High-Level Design

Two-server architecture with shared SQLite database:

```
deepseek-proxy (port 4570)          deepseek-dashboard (port 4571)
┌──────────────────────┐            ┌──────────────────────┐
│ FastAPI (existing)    │            │ FastAPI (new)         │
│ + DashboardInstrument │ WebSocket │ + REST API            │
│ or (hook/emit)        │◄─────────►│ + WS forward to FE    │
│                       │  events   │                       │
│ Writes:               │            │ Reads:                │
│  • dashboard.db       │            │  • dashboard.db       │
│  (SQLite WAL)         │            │  (SQLite WAL)         │
└──────────┬────────────┘            └──────────┬────────────┘
           │                                    │
           │ SQLite WAL (shared)                │
           ▼                                    ▼
    ┌──────────────────────────────────────────────┐
    │              dashboard.db                      │
    │  tables: conversations, metrics, tool_calls,  │
    │          anomalies, account_sessions,          │
    │          chat_correlations                     │
    └──────────────────────────────────────────────┘
```

### Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Number of servers | 2 (proxy + dashboard) | Isolation - dashboard crash does not affect proxy. User explicitly chose this. |
| Database | SQLite WAL mode | Zero-config, single file, sufficient for single-user workload |
| Proxy integration | Instrumentation hooks | Minimal code changes to existing proxy (4-5 lines in ProxyService) |
| Real-time | WebSocket (proxy→dashboard→FE) | Low latency, bidirectional when needed |
| Frontend | React + Vite + TypeScript | User explicitly chose React/Vite/TS |
| Auth | Single admin JWT | One user, one password (bcrypt hash in env) |

## Database Schema

### SQLite WAL Mode — `dashboard.db`

**Shared between proxy (writer) and dashboard (reader).**

#### Table: conversations

| Column | Type | Description |
|--------|------|-------------|
| id | TEXT PK | UUID generated by proxy |
| chat_id | TEXT | DeepSeek session ID (from watermark) |
| account_slot | INTEGER NOT NULL | 0, 1, or 2 |
| user_uuid | TEXT NOT NULL | Client UUID (from watermark) |
| model | TEXT | deepseek-v4-pro / deepseek-vision |
| status | TEXT | active / completed / error / interrupted |
| started_at | REAL NOT NULL | Unix timestamp (seconds) |
| ended_at | REAL | Unix timestamp |
| total_tokens | INTEGER | Total tokens used |
| total_duration_ms | INTEGER | Total duration in ms |
| error_message | TEXT | Error details if status = error |

Indices: `user_uuid`, `account_slot`, `status`, `started_at`

#### Table: metrics

| Column | Type | Description |
|--------|------|-------------|
| id | INTEGER PK AUTO | Auto-increment |
| conversation_id | TEXT FK | References conversations.id |
| timestamp | REAL NOT NULL | Unix timestamp |
| ttft_ms | REAL | Time To First Token |
| tokens_per_sec | REAL | Token generation speed |
| tokens_total | INTEGER | Cumulative tokens |
| latency_ms | REAL | Last chunk latency |
| events_count | INTEGER | Tool call count |
| stream_active | INTEGER | 1 if streaming |

#### Table: tool_calls

| Column | Type | Description |
|--------|------|-------------|
| id | INTEGER PK AUTO | Auto-increment |
| conversation_id | TEXT FK | References conversations.id |
| tool_name | TEXT NOT NULL | Tool function name |
| arguments | TEXT NOT NULL | JSON arguments |
| result | TEXT | JSON result |
| is_valid | INTEGER | 1 = valid, 0 = repaired/failed |
| repair_tier | INTEGER | 0=OK, 1/2/3=repair tier |
| parsed_at | REAL NOT NULL | Timestamp |

#### Table: anomalies

| Column | Type | Description |
|--------|------|-------------|
| id | INTEGER PK AUTO | Auto-increment |
| conversation_id | TEXT FK | References conversations.id |
| type | TEXT NOT NULL | high_latency / stream_error / tool_repair / rate_limit / etc. |
| severity | TEXT | info / warning / critical |
| message | TEXT NOT NULL | Human-readable description |
| details | TEXT | JSON with additional data |
| detected_at | REAL NOT NULL | Unix timestamp |
| acknowledged | INTEGER | 0 = unread, 1 = acknowledged |

#### Table: account_sessions

| Column | Type | Description |
|--------|------|-------------|
| id | INTEGER PK AUTO | Auto-increment |
| slot | INTEGER UNIQUE | 0, 1, 2 |
| status | TEXT | inactive / active / rate_limited / error |
| rate_limited_until | REAL | Timestamp until rate-limited |
| conversations_count | INTEGER | Total conversations handled |
| last_used_at | REAL | Last usage timestamp |
| created_at | TEXT | ISO datetime |
| last_login_attempt | TEXT | ISO datetime |

#### Table: chat_correlations

| Column | Type | Description |
|--------|------|-------------|
| id | INTEGER PK AUTO | Auto-increment |
| correlation_key | TEXT NOT NULL | Hash key (UUID, topic hash) |
| conversation_id | TEXT FK | References conversations.id |

### WebSocket Events

Proxy → Dashboard WebSocket connection:

| Event | Direction | Payload |
|-------|-----------|---------|
| `conversation:started` | proxy → dashboard | `{conv_id, account, user_uuid, model}` |
| `conversation:metric` | proxy → dashboard | `{conv_id, ttft, tps, latency, tokens}` |
| `conversation:completed` | proxy → dashboard | `{conv_id, total_tokens, duration_ms}` |
| `conversation:error` | proxy → dashboard | `{conv_id, error_message}` |
| `anomaly:detected` | proxy → dashboard | `{conv_id, type, severity, message}` |
| `account:status_change` | proxy → dashboard | `{slot, status, rate_limited_until}` |

Dashboard forwards these events to the React frontend via Socket.IO.

## Proxy Instrumentation

The `DashboardInstrumentor` hooks into existing `ProxyService.stream_completion()`:

```python
# Pseudocode — minimal insertion points in existing code

class ProxyService:
    async def stream_completion(self, request, ...):
        # 1. [NEW] instrumentor.on_conversation_started(...)
        #    — after session creation, before stream

        async for chunk in ds.stream_completion(session, prompt):
            # 2. [NEW] instrumentor.on_metric(...)
            #    — on each chunk, with ttft, tps, latency

            yield chunk

        # 3. [NEW] instrumentor.on_conversation_completed(...)
        #    — after stream ends

        # 4. [NEW] instrumentor.on_anomaly(...) on errors/repairs
```

### UUID Watermark Extension

Existing watermark: `<!-- PROXY_CHAT: {chat_id} -->`

Extended watermark: `<!-- PROXY_CHAT: {chat_id} | PROXY_UUID: {user_uuid} -->`

The UUID is generated on first request (no existing UUID in conv_state) and stored in `conv_state.json` alongside `chat_id`.

## Anomaly Detection Rules

Anomalies are detected in `DashboardInstrumentor` based on real-time metrics:

| Anomaly Type | Condition | Severity |
|-------------|-----------|----------|
| `high_latency` | TTFT > 15s or per-chunk latency > 5s | warning |
| `stream_error` | Stream disconnect, timeout, or HTTP error | critical |
| `tool_repair` | Tool call repaired by Tier 2 or Tier 3 | info |
| `rate_limit` | Account enters rate-limited state | warning |
| `high_error_rate` | >30% error rate in last 10 conversations | critical |
| `empty_response` | Response with 0 content tokens | warning |
| `long_conversation` | Duration > 5 minutes | info |

## Chat Correlation Mechanism

Three correlation dimensions:

1. **User UUID** — all conversations sharing the same UUID are grouped
2. **Parent-child threading** — existing `parent_id` tracking in proxy state reproduced as conversation tree
3. **Semantic similarity** (optional/future) — TF-IDF + cosine similarity analysis of prompts for automatic topic clustering

Correlation data is displayed as a force-directed graph where nodes are conversations and edges represent relationships (same UUID, parent-child, same topic).

## Authentication

Single admin user. Password stored as bcrypt hash in environment variable `DASHBOARD_PASSWORD_HASH`. Default password is generated on first run and printed to console.

JWT tokens expire after 24 hours. All `/api/v1/*` endpoints (except `/auth/login`) require `Authorization: Bearer <token>` header.

## Future Considerations

- Migration to PostgreSQL for multi-user support
- Migration to single-process monolith if two-server overhead proves unnecessary
- Semantic similarity for automatic topic-based correlation
- Export to CSV/JSON for conversation data
- Prometheus metrics export for integration with existing monitoring infrastructure
